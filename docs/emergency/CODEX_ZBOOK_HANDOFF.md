## 4. Codexが最初に行う作業

### A. 実行場所を確認して診断する

現在の実行環境がZBook本体、既存Linuxゲスト、クラウドのどれかを確認する。ZBookで実行できる場合は、まずリポジトリのルートから次を実行する。

```powershell
py -3 .\scripts\check_emergency_workstation.py
```

診断ファイルだけを保存したフォルダーなら `py -3 .\check_emergency_workstation.py`。既存Linux実行環境に通常の方法でアクセスできる場合は、その環境でも別に実行する。

```bash
python3 scripts/check_emergency_workstation.py
```

- 診断は追加パッケージ不要。`py` 等が見つからなければエラーを記録し、既存の利用可能な実行経路を確認する。診断だけのためにインストールや管理者権限取得を始めない。
- 既存の8787・8796・8797、VM、WSL、worktreeを起動停止・変更しない。
- `diagnostic_status=COMPLETED` は収集終了の意味。各probeの失敗・不明を成功や「存在しない」に変えない。
- `--context workstation` は実行者の申告ラベルであり、ZBook実機であることの証明ではない。
- クラウドでしか実行できない場合は、その結果をZBookの結果にしない。利用者から必要なのは実機の診断結果であり、実帳票や鍵のチャットへの転送ではない。

診断出力は必要な項目だけ内部で記録する。想定外の識別情報が含まれていないことを確認し、公開GitHub/CIへ端末の生出力を貼らない。

### B. 実行環境を決めて合成帳票を通す

現行の原本読取・PDF生成はLinux専用。Windows対応のために子プロセスの制限を外さない。WindowsのGPUとLinuxゲストのGPU、RAM、空き容量を分けて確認する。WindowsのモデルサービスとLinuxゲストのloopbackは別物として接続を確かめる。

診断結果から、既存環境と衝突しない専用release・venv・DB・鍵・原本保存先・一時領域・API・ワーカーを用意する。空きポートは現地で確認する。必要資材が不足する場合は具体的な不足を記録し、勝手にモデルを取得しない。

合成帳票で「取込 → 原本表示 → 読取確認 → 検査 → 訂正確認用PDF → 訂正版取込 → 再検査」を実行し、対象commit・環境・実行結果を残す。実帳票は保護条件と取扱い範囲を確認した環境内で扱い、`synthetic` と偽って取込条件を回避しない。

### C. 正式帳票の現物から基準評価を始める

空の現行正式帳票と入力要領を内部で確認し、ページ、欄、単位、非印字、適用期間を対応させる。既存の433行は重複を含む候補台帳であり、承認済みの433ルールではない。P01の二次校閲・採否、P03の現行正式資料、P04の正式欄対応の未完了を保持し、一括有効化しない。

印字PDF・画像PDF・手書き訂正・二重線・略語・空欄を区別する。原本に実際に書かれた文字の転記と、正しい訂正先を別管理し、別担当者が確認する。「訂正済み」「最終版」だけで正解にせず、訂正前の原本がなければ誤りを推測で復元しない。

この段階から5指標の比較条件・作業時間・提出・追跡を並行して記録する。再学習の終了まで測定開始を待たない。

## 5. 続けて実装する必須残件

実機と正式帳票の基準結果から最初の学習タスクとモデルを選ぶ。画像読取と本文の記載確認を分け、未確認のGPU容量からモデル・量子化・batch・所要時間を決め打ちしない。

1. 独立した正解記録、原本と改訂・再スキャン・切出しを束ねるfamily、固定dataset registryを追加する。
2. 同じfamilyがTrain・Validation・Holdoutへ混ざらないことを強制する。基準モデルと入力・正解・前処理版を固定する。
3. 学習jobと実トレーナー、checkpoint・モデルartifactの版管理を実装する。既存vaultの容量制限を踏まえ、保護されたモデル保管と復元を設計する。
4. 実際のoptimizer stepと重みの変化、保存、新規プロセスでの再読込・推論を確認する。小規模合成モデルでの工程試験と、過去の実帳票での学習を別の結果にする。
5. 固定評価、実配備形式での比較、独立確認、昇格・rollbackをつなぐ。学習に成功しただけで本番へ昇格させない。

現行の `emergency_audit_learning.py` は傾向集計、`learning_engine.py` の `literal-correction-v1` は置換処理である。辞書、RAG、prompt変更を「モデル再学習が完了した」と報告しない。

実機や資料の待ちがあっても、既存契約に基づく正解・family・分割漏えい防止等の実装と合成試験は進める。待ちである理由と必要な入力を絞って記録し、計画を書いただけで全開発を止めない。正式判断・独立正解・本部側の承認をCodex自身で代行して済ませない。

## 6. 5指標の実測で守ること

| 指標 | 実測の条件 |
| --- | --- |
| 提出後訂正率の減少 | 比較条件と同じ追跡期間を固定し、実際の提出後の訂正を記録する。開始日に削減率を作らない |
| 提出前の誤り発見 | 独立確認で見逃しも登録し、実際の警告・提出時刻で判定する。過去帳票の再検査を過去の提出前発見に数えない |
| 正しい記載への誤警告 | 独立確認した誤警告の件数と割合を表示する。未確定や警告0件を都合よく0%にしない |
| チェックと訂正の合計時間 | 取込から再検査、別担当者確認、提出後対応まで人・分を記録する。欠測を0分にしない |
| 読取不能・未検査の区別と情報保護 | 原本との照合に加え、対象実機の通信、権限、保存、一時ファイル、ログ、復元の証拠を残す |

最低件数、目標値、追跡日数、許容劣化は未確定。評価条件を最終判定前に固定し、不足する間は保留とする。モデル比較の学習前baselineと、既存運用の `baseline`（支援なし）を混同しない。技術benchmark、実運用5指標、本番受入は別に記録する。

原本、教師データ、詳細評価、学習済み重み・checkpoint、鍵、患者・隊員情報は公開GitHub/CIに入れない。訂正確認用PDFにも原本の個人情報が含まれ得る。原本不変・専用権限・版競合・失効確認を維持し、正式原本への自動上書きは追加しない。

## 8. 作業の残し方
