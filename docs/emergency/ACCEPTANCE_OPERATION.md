# 5指標の測定・完成評価：利用と運用

基準日: 2026-11-21（日本時間）。本書は5指標の評価管理画面の手順。原本読取・チェック・訂正の画面は [監査システム運用手順](AUDIT_OPERATIONS.md) を参照する。どちらも本部への導入済み宣言ではない。

## 画面の開き方

既存の業務画面にログインし、「救急業務」から「チェックの完成評価」を開く。画面のパスは `/ui/emergency-acceptance.html`。救急事案・傷病者個票・救急集計の3つの参照権限が必要。一般の集計権限だけでは表示・取得できない。

1. 初回は「合成データで操作確認」で、未読の見逃しと追跡中の例を確認する。表示される値は実績ではない。
2. 監査画面の「測定記録を保存」で作成したJSON、または評価担当者が本部内で独立に作成した所定の測定記録を取り込む。監査画面は実際の履歴・確認・提出・作業記録から出力し、通常の作成者にJSON編集を求めない。原本PDFや氏名を入れた自由形式ファイルを評価画面に渡さない。未記録の提出・不明な正解などは出力時にも未確定または保留となる。
3. 数値目標と最低件数は空欄から設定する。「再計算」で不足・保留を確認し、「保存」で不変の評価記録を残す。目標の設定は本部による正式承認そのものではない。
4. 訂正は履歴から最新の評価を選び、新しい版を作成する。以前の記録は消さない。新版ができた旧評価は確認・再訂正できない。
5. 登録者とは別の職員が、独立正解確認・比較条件・必要な証拠を確認する。「確認済み」は評価記録の確認状態であり、本番導入の承認ではない。

画面には、各指標の分母と件数、観察中・欠測・正解未確定、事案/帳票の構成を表示する。警告のうち誤警告の割合は未確定警告が残ると未測定にする。確定済みの正解だけに基づく発見率はその範囲を明記し、全体の確定値とは表示しない。

## 記録の契約

`backend/app/emergency_acceptance_schemas.py` が形式の正本。例は権限付きの `GET /emergency/acceptance/sample` で取得できる。例を実測値へ書き換えて実績と見なしてはならない。監査画面では不変の原本・実行・人の確認へ紐付け、提出前に存在した原本版を測定範囲にする。外部から手動で作成する測定記録では、同じ対応表と範囲を本部内で管理する。

- 無作為の評価用ID、比較群、報告書版、事案/帳票区分、観察状態、誤りと警告、読取状態、作業区間を記録する。
- 1つの入力に同じ報告書を複数行で入れたり同じ検査機会を重ねたりしない。提出前原本の再チェックは別の実行として紐付け、繰り返し出た警告の負担を残す。同じ実際の誤りは独立確認者が共通の誤りIDで紐付け、発見数を増やさない。`report_version` は基準原本の版であり、全警告がそのPDF1枚だけに由来するという意味ではない。
- 作業区間は報告書ごとの相対秒。1件内の同じ職員の重複時間を拒否し、別職員の同時作業は合算する。複数報告書を並行処理した場合の時間割当は収集側で重複させない。
- 提出後の観察が未完了、訂正の有無が不明、作業計測が未完了なら、確定した合計時間へ入れない。未計測と実測0は別扱い。
- 1要求2 MiB以下、報告書1,000件以下、検査機会合計20,000件以下。資源保護の上限であり、100人同時利用や年間保存容量の実測保証ではない。上限に達する評価集合は、集計を独立標本と誤解しない収集方法を別途設計する。

## サーバー運用

本番DBは既存仕様どおりPostgreSQL。新規migrationは `059_emergency_acceptance.sql`。既存の移行手順で適用し、過去のmigrationを編集しない。個々の利用者端末へ追加インストールする変更ではない。

初期状態では合成データだけを登録・参照できる。本部内実測は `FIRE_AI_EMERGENCY_ACCEPTANCE_INTERNAL_ENABLED=true` を、組織が承認した内部環境に限って設定する。このスイッチはネットワーク遮断・暗号化・バックアップ等を自動実証するものではない。

APIは既存の認証、固定本部、権限失効、書込時の再検証を使用する。参照は `emergency.case.read` / `emergency.patient.read` / `emergency.report.read`、保存はさらに `emergency.report.create`、独立確認はさらに `emergency.report.review` が必要。証拠資料の参照には `document.read` も必要。新しい権限の自動付与はしない。

証拠は既存の本部内文書登録で `document_type=emergency_acceptance_evidence` として管理し、評価の確認時に参照する。原本の名称・内容を評価APIへ複製せず、内部の文書参照とその版のハッシュを保存する。資料の内容、対象環境、コード/ルール/帳票の版、試験手順・結果が今回の評価に一致するかは、別職員が確認する。単に文書IDを登録しただけで安全性が証明されるわけではない。

監査には操作種類、評価ID、版、件数、確認状態だけを記録する。APIの不正入力は固定のエラー文に変換し、入力値や任意のキーを返さない。応答は `no-store`、画面は評価データをlocalStorage/sessionStorageへ保存しない。セッション・権限の変更時には結果と入力を消去する。リバースプロキシ、サーバーログ、実機キャッシュ、バックアップ等の配置先での確認は別途必要。

## 候補チェックの接続

`POST /emergency/acceptance/candidate-checks` は、許可された正規化項目だけを既存の候補判定核へ渡す。入力値はこのAPIでは保存せず、判定の件数だけを監査に記録する。型が異なる値は拒否し、未読・未確認・非印字・未対応は未検査として残す。

この一時入力APIのルールはすべて `PROVISIONAL_NOT_APPROVED`、提出可否は `NOT_PROVIDED`。PDFからの読取・原本位置・本人確認・設定承認・再チェックは、別の `/emergency/audit` に実装した。どちらも原システムへ自動で書き戻さない。

## 検証と残る受入

合成データによる指標・API・旧判定核・画面JS・P01文書ゲートの関連試験を実行し、171件合格、4件未実行（PostgreSQL1件、実ブラウザ3件）を確認した。独立レビューの指摘は修正し、回帰で再確認した。この件数は当該ローカル実行の証拠であり、実帳票の精度や全体CI合格とは別である。

CIでは既存のPostgreSQLサービスを使って移行・並行確認・DB不変性を検証し、実ブラウザの専用jobで操作・共有端末の失効・遅延応答を検証する。対象commitの結果はPR #142のChecksを参照する。必要なskipを成功件数に含めない。

正式な完成には、現行正式資料・実様式の承認、実帳票のOCR/手書き/本文候補の品質、訂正ループの現場確認、独立した実運用比較、実機の情報保護・復元・更新・本番承認が残る。機能の接続は監査パイプラインに実装済みでも、その実用性の証明を合成テストで代替しない。

2026-11-22の利用者指定で、ZBookでの正式帳票検証と、過去帳票によるモデル重みの再学習を必須工程に追加した。現在の傾向集計は実学習ではなく、実際の学習・再読込・未使用帳票での比較は未実行。[実機検証手順](ZBOOK_PILOT.md)と[必須再学習仕様](MODEL_RETRAINING.md)に従い、実装未完・未測定を残す。過去帳票の再検査を、過去の提出前に発見した実績として数えない。
