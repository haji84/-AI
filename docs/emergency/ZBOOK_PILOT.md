# ZBookで正式帳票と5指標を検証する

更新日: 2026-11-22。これは実機で行う手順であり、実施済みの記録ではない。

## 今回の完成条件

本人のZBookで正式な救急報告書を読み取り、修正箇所と根拠を記載したPDFを出し、過去帳票でモデルを実際に再学習する。再学習前後の精度と、実運用の5指標を記録する。既存OAへの自動書戻しは対象外。

現在の作業環境はクラウドLinuxであり、ZBookではない。ZBookへの直接実行経路は確認できていない。過去の機種情報や合成テストを、現在の実機性能・実帳票精度として記録しない。

## 1. 最初の操作は読取専用診断

ZBookでVS Codeのターミナルを開き、ダウンロードした `check_emergency_workstation.py` があるフォルダーで実行する。

```powershell
py -3 .\check_emergency_workstation.py
```

このリポジトリのルートで実行する場合は、代わりに次を使う。

```powershell
py -3 .\scripts\check_emergency_workstation.py
```

結果のJSONを確認する。診断に追加のPythonパッケージは不要。`py` 自体が利用できない場合は、インストールへ進まず、そのエラーで実行経路の未確認を記録する。

診断はOS、CPU数、RAM、匿名化した領域の容量、GPU/VRAM、Python、OCR、ローカルモデルサービス、仮想マシンの匿名化した稼働・割当資源の状態を限定して調べる。取得できない項目は不明・権限不足として残す。プログラムやモデルの取得、推論、VM/WSLやサービスの起動停止、鍵の生成、報告書の読込はしない。既存の8787・8796・8797、worktree、VMは変更しない。

結果にはマシン名、ユーザー名、実パス、VM名、IP、トークン、原本を含めない。実際の報告書を診断結果と一緒に公開リポジトリやCIへ送らない。

## 2. Windows本体と実行環境を別々に確認する

現行の原本読取・PDF生成はLinuxの制限付き子プロセスで動作する。Windows直接実行を有効化するために、この制限を外さない。

利用可能な既存Linuxゲストがある場合、通常のアクセス方法で入った後に同じ診断を実行する。

```bash
python3 scripts/check_emergency_workstation.py
```

診断のためにVMを自動起動したり、既存VMを変更したりしない。WindowsでGPUが見えてもLinux内で使えるとは限らない。Windows側とゲスト側の空きRAM・ディスク・GPU認識を別に記録する。

モデル接続は監査の実行環境内のloopbackを使う。Windows側のOllamaとLinuxゲストのloopbackは別の接続先である。既存モデルが表示されることだけで、監査からの利用や再学習が可能と判定しない。

現地の値が分かるまで、使用モデル、学習方式、入力長、処理件数、所要時間、必要空き容量は固定しない。

## 3. 別インスタンスとして試験環境を用意する

診断結果から利用できる実行環境を選び、[監査運用手順](AUDIT_OPERATIONS.md)に従って専用のrelease・venv・DB・鍵・原本保存先・一時領域・API・ワーカーを用意する。既存サービスのポートや設定を上書きしない。空きポートは実機で確認する。

合成帳票で取込、原本表示、読取確認、チェック、PDF出力、訂正版の再読込まで通す。その後、対象環境の保護条件を確認して本部内の実帳票を扱う。実帳票を `synthetic` と偽って取込条件を回避しない。

必要な接続確認は次のとおり。

| 確認 | 残す証拠 |
| --- | --- |
| 実行版 | release/commit、Python・ネイティブ読取・OCR言語データの版とハッシュ |
| DBと権限 | 本部identity、専用閲覧・作成・確認・出力権限、他利用者の拒否と失効 |
| 原本保管 | 原本SHA、暗号化保存、鍵の別管理、一時領域とログに残る情報 |
| 読取ワーカー | 待ち行列、再起動、期限超過・容量不足時の状態と原本の保持 |
| モデル | 実行側での応答、モデルとtokenizerの実体・版、外部通信・ログ、推論時間と資源使用 |
| 復旧 | 対応するDB・暗号化原本・別保管鍵からの復元結果 |

診断が正常に終了したことと、これらが実証済みであることを混同しない。

## 4. 正式帳票を読み取る

まず、現行の空の正式帳票と入力要領を内部の「帳票とルール」に登録する。ページ、欄、型、単位、印刷されない項目、適用期間を実物から対応させる。旧様式との対応を推測しない。設定と正式資料を別担当者が照合する。

次に、取扱いを認められた環境内で実際のPDF・スキャンを取り込み、原本と読取候補を並べて確認する。印字PDF、画像だけのPDF、手書き、二重線、略語、空欄を区別して結果を残す。正式帳票であることと、記載が正しいことは別に確認する。

略語を一意に解釈できない場合や手書きの訂正が誤っている可能性が残る場合は未確定とする。「最終版」「訂正済み」という属性だけで正解にしない。ここでの読取結果を独立確認した基準値と比較して、欄ごとの誤読・未読・誤った確認済みを記録する。

## 5. 修正箇所のある報告書を出力する

確認結果の下の「訂正確認用PDF」を押す。出力権限が必要。現在原本の最新検査を対象に、原本表示のコピーへ番号と枠を付け、日本語の指摘一覧を付ける。

- 要修正と担当者が確認した箇所、未確定の確認候補、読取不能、未検査を分ける。
- 位置を特定できない指摘は「位置未特定」とし、適当な欄へ枠を付けない。
- 正しい修正文が未確認なら生成して埋めない。
- 出力対象は表示中の検査1件。ルール、本文AI、画像候補を別々に実行した過去結果は勝手に合成しない。種別と範囲をPDFに表示する。
- 古い原本・古い結果・版不一致・設定失効では、再読込または再検査が必要。

これは別ファイルの訂正確認用コピー。正式原本や電子署名を置き換えない。元OAでの修正後に正式PDFを再出力し、新しい版として読み込んで再検査する。PDFコピーも原本の個人情報を含み得るので、内部の所定の保存先で扱う。

## 6. 過去帳票で実際に再学習する

[必須再学習仕様](MODEL_RETRAINING.md)に従う。現行の訂正傾向集計は学習器ではなく、現在は実学習を完了していない。

正式帳票の基準評価で、誤読が主な課題なのか、本文の不整合検出が主な課題なのかを把握して学習対象を決める。独立確認した正しい転記・訂正内容を用意し、同一事案の原本・訂正版・再スキャン・ページを学習用と評価用にまたがらせない。

モデルの重み更新、保存、新しいプロセスでの再読込、固定評価帳票での比較を実行する。単なる辞書更新や過去事例の検索を再学習完了に数えない。学習前モデルと学習後候補を別に保持し、改善しない候補を自動で実運用へ反映しない。

## 7. 5指標の実測を始める

[測定仕様](ACCEPTANCE_MEASUREMENT.md)の分母・対象原本・独立確認を使う。比較区分を最初のチェック前に記録し、実際の作業時間、提出日時、提出後追跡を保存する。既存の「作業記録」と「5つの評価指標」画面を使う。

| 指標 | 試験開始時にすること | 数値を確定できる条件 |
| --- | --- | --- |
| 提出後訂正率 | 支援なし/支援ありの比較条件と追跡期間を先に固定する | 実際に提出し、同じ追跡期間を完了した記録がある |
| 提出前の誤り発見率 | 原本全体を別担当者が確認し、指摘のない箇所の誤りも記録する | 実際の警告時刻・提出日時・固有の誤り・対象範囲が確定している |
| 誤警告 | 全警告を独立に確認し、未確定を残す | 評価対象の警告と正解が確定している |
| 合計作業時間 | 取込・原本確認・訂正・再チェック・別担当者確認・提出後対応を計測する | 欠測がなく、重複時間と担当者を確認している |
| 読取/未検査と情報保護 | 読取状態を照合し、実機で通信・保存・権限・復元を確認する | 対象環境と版に結び付いた独立確認の証拠がある |

過去帳票を今から検査する試験は、固定資料を使った技術的な精度評価である。今出した警告を過去の提出前警告として登録しない。既存の「支援なし導入前群」は、学習前モデルを動かす群ではない。

最低件数・合格数値・追跡日数は、現物と現場の訂正周期を確認してから固定する。未確定の値を仮の実測値で埋めない。学習データ作成と再学習・保守の時間も、報告書1件の確認時間と分けて記録する。
