# 救急報告書監査：内部サーバーの導入・運用

## 対象と現在の境界

v1の対応配置は **Linuxサーバー + 本部内ブラウザー**。利用者のWindows端末にはPython・OCR・Excel/VBA・追加アプリを入れない。既存OAから許可された方法でPDFを出力し、承認済みの内部URLへ取り込む。Windows上でのサーバー直接実行は、ネイティブ処理の子プロセス停止・資源制限を未検証のため `PROCESS_PLATFORM_UNSUPPORTED` で拒否する。

原本・読取結果・画像AIの候補・確認値・チェック履歴は専用の権限と暗号化領域で扱う。汎用の `/documents` や外部ストレージへ置かない。本書のコマンドはサーバー管理担当者向けであり、OA端末での実行を求めるものではない。

合成データでの動作確認、実機の導入確認、実帳票の精度・5指標の受入は別の証拠として残す。ホストチェックが成功しても、本番運用・医学的判断・帳票読取精度の承認にはならない。

関連正本：[本部別配置](../architecture/TENANT_OPERATIONS.md)、[導入用構成](../../deploy/tenants/README.md)、[監査API](AUDIT_API_V1.md)、[完成目標](REPORT_CHECK_GOAL.md)、[5指標](ACCEPTANCE_MEASUREMENT.md)。

本人のZBookでの最初の検証は [ZBook実機検証](ZBOOK_PILOT.md) に従う。最初に読取専用診断を行い、Windows本体とLinux実行環境を区別する。過去帳票によるモデル再学習は2026-11-22に追加された必須工程であり、現行の傾向集計では代替しない。実装・実行の残項目は [必須再学習仕様](MODEL_RETRAINING.md) に記録する。

## 1. サーバーに用意するもの

既存の本部別DB、専用OSユーザー、専用venv、TLS、Host、原本保存先、バックアップ先を再利用する。新規本部は `scripts/generate_department_config.py` の生成物を管理者が確認して配備する。本部UUID、DB資格情報、OSユーザー、storage、backupは本部間で分離する。

監査機能を使う本部の構成生成では、既存の指定に **`--emergency-audit`** を追加する。生成先には新しいレビュー用ディレクトリを指定し、既存の本番設定へ直接上書きしない。既存本部では同じ本部UUID・対象releaseを使い、資格情報や他のwriter一覧を引き継いで変更箇所を確認する。

| 生成物・設定 | オプションなし | `--emergency-audit` あり |
|---|---|---|
| 監査機能 | `FIRE_AI_EMERGENCY_AUDIT_ENABLED=false` | `true` を含む配備用設定を生成 |
| 実帳票の利用許可 | `FIRE_AI_EMERGENCY_AUDIT_INTERNAL_ENABLED=false` | 同じく `false`。別途受入が必要 |
| 監査ワーカー | 生成しない | 本部専用unitを生成 |
| バックアップwriter | 監査ワーカーを登録しない | 生成した監査ワーカーを登録 |
| 一時領域 | 通常のAPI設定 | APIとワーカーに別々の専用 `/run` 領域 |
| 鍵・OCR・モデル | 作成・導入しない | 作成・導入しない。鍵とmanifestの配置先だけを記載 |

このオプションは構成ファイルの生成のみであり、サーバーへのインストール、有効化、起動、モデルダウンロードを行わない。初期状態で監査を使わない本部のバックアップが、未導入の監査ワーカーを探して失敗する構成にはしない。生成器のPython APIも `render_department(..., emergency_audit=False)` が既定で、既存呼出しはそのまま利用できる。

承認した配布物には次を揃える。

- 対象commit/release、適用済みDB migration、`backend/requirements-release.lock` に対応したPython wheel一式。
- Linux用Tesseract本体・ネイティブ依存ライブラリ、`jpn.traineddata` と `eng.traineddata`。Pythonの `pytesseract` を入れるだけではOCR本体や日本語データは入らない。
- 承認済みネイティブmanifest。実行ファイルのバージョン/SHA-256と、使用言語データのSHA-256を記録する。
- AIを使う場合は、別途審査したローカルモデル、モデルを動かすサービス、その配布物/モデルの版・ハッシュ・ライセンス・外部通信/ログ設定。未設定なら画面は `NOT_CONFIGURED` のまま利用できる。
- 監査専用暗号鍵の別保管と復旧手順、メモリー上の一時領域、監査ワーカーのservice設定。

閉域向けに、上記を事前に検証した内部配布媒体へまとめる。実行時にパッケージ・学習済みデータ・モデルをダウンロードする処理はない。AIアダプターもモデルのpullは行わない。

venvへの依存導入は既存のrelease手順に従う。内部wheel置場を使う場合の操作例：

```bash
/opt/fire-ai/venv/bin/python -m pip install --no-index --find-links /srv/fire-ai-approved-wheels --require-hashes -r backend/requirements-release.lock
```

上記は配置例。生成済みの本部別release/venvパスを使用し、実機のPython・OS・CPU向けに検証済みのwheelを揃える。ネイティブOCRとモデルはPython wheelとは別に配備する。

## 2. 鍵を初期化する

`FIRE_AI_EMERGENCY_AUDIT_KEY_FILE` は本部専用の32バイト鍵を指す。キーはstorage、通常backup、release/Gitの外へ置く。親ディレクトリを専用OSユーザーの0700、鍵を0600とし、他ユーザー・他本部から読めないことを確認する。

本部別生成物では `/etc/fire-ai/keys/<slug>-emergency-audit/audit.key` を指定する。管理者がその親ディレクトリだけを当該 `fireai_<slug>` ユーザーの所有・0700で作成する。他本部の鍵やバックアップ受取人鍵まで共通ユーザーの所有へ変更しない。

専用OSユーザーへ本部の保護された環境変数を渡したうえで、**初回だけ**実行する。

```bash
/opt/fire-ai/venv/bin/python scripts/check_emergency_audit_host.py --initialize-key
```

これは明示的な作成操作。既存ファイルを上書きしない。成功時は `KEY_CREATED`、既存なら `KEY_ALREADY_EXISTS`。鍵値やファイルパスは標準出力へ出さない。相対パス、symlink、storage/既知のbackup配下、共有された親ディレクトリは拒否する。独自backup先がある場合は `--backup-root` を追加して除外範囲を明示する。

鍵の原本と復旧用控えは、組織が承認した別の鍵保管経路で管理する。**更新時に鍵を再生成しない。v1には無停止の鍵ローテーション機能はない。** 鍵を失うと既存の暗号文を復号できない。バックアップの外側を暗号化するX25519鍵と、この監査用AES鍵は別物である。

## 3. ネイティブmanifestと読取装備を確認する

manifestの形式は以下。山括弧の値は説明用であり、実機で採取・照合して承認した値に置き換える。例をそのまま登録しても検証を通らない。

```json
{
  "schema_version": 1,
  "tesseract": {
    "version": "<承認した実バージョン>",
    "executable_sha256": "<実行ファイルの64桁SHA-256>",
    "traineddata": {
      "jpn": "<jpn.traineddataの64桁SHA-256>",
      "eng": "<eng.traineddataの64桁SHA-256>"
    }
  }
}
```

`tesseract --version`、`tesseract --list-langs` と、対象実ファイルのSHA-256を管理者が照合する。manifestは管理者が承認した配布物と照合し、サービスから書き換えられない場所へ置く。現状の機械から値を採取しただけで承認済みにしない。

`FIRE_AI_EMERGENCY_AUDIT_NATIVE_MANIFEST` を設定するか、明示的に指定する。

```bash
/opt/fire-ai/venv/bin/python scripts/check_emergency_audit_host.py --manifest /etc/fire-ai/approved-native.json
```

通常実行は読取専用。ダウンロード・モデル起動・鍵生成・DB書込・報告書の読み込みを行わない。固定形式JSONだけを返し、秘密値・ファイルパス・原本を出さない。終了コード0はこの読取装備の事前条件が揃った状態、2は不足/不一致。主な確認項目：

| 結果 | 意味・対応 |
|---|---|
| `MANIFEST_REQUIRED` | 承認したmanifestを指定する。 |
| `NATIVE_EXECUTABLE_MISMATCH` / `NATIVE_VERSION_MISMATCH` | 配布した本体と承認対象が一致しない。更新承認と実体を確認する。 |
| `OCR_LANGUAGE_UNAVAILABLE` / `NATIVE_LANGUAGE_MISMATCH` | 指定した言語データがない、または版が一致しない。日本語を英語へ置き換えて成功扱いしない。 |
| `KEY_*` / `PRIVATE_STORAGE_UNAVAILABLE` | 鍵の設定・配置・所有者・アクセス権を確認する。既存鍵の再生成はしない。 |
| `DISK_BACKED_OR_UNKNOWN` | 一時領域がtmpfs/ramfsと確認できない。メモリー上の専用一時領域を設定する。 |
| `CONFIGURED_NOT_VERIFIED` | AIモデル名の設定はあるが、実モデルの存在・応答・品質は未検証。 |

GPUはこのチェックでは未検証であり、活字OCRにGPU必須とはしていない。DB接続、本部identity、ワーカーの継続動作、AIの実応答、実帳票精度は別に確認する。`production_accepted` は常にfalseである。

## 4. 一時領域とワーカーを起動する

PyMuPDFによる原本処理/描画はメモリー内で行う。pytesseractは一時画像・TSVを使うため、`TMPDIR` を本部専用0700のtmpfs領域へ向ける。ワーカーはその下に毎回0700の子ディレクトリを作り、成功・エラー・タイムアウト後に削除する。

[`fire-ai-emergency-audit-worker.service`](../../deploy/systemd/fire-ai-emergency-audit-worker.service) は単一本部配置用テンプレート。`RuntimeDirectory`、`TMPDIR`、専用ユーザー、EnvironmentFile、release/venv、ReadWritePathsを実際の本部設定へ合わせる。`/run` がメモリー上の領域であることもホストチェックで確認する。`ExecStartPre` はmanifest・鍵・一時領域の確認を通過してからワーカーを起動する。

本部別構成では、`--emergency-audit` で生成した `fire-ai-<slug>-emergency-audit-worker.service` を使う。本部専用のユーザー、env、release、venv、書込先が反映される。上記の単一本部テンプレートをそのまま複数本部で共用しない。

生成したAPIとワーカーのunitを一緒に配備する。APIは `/run/fire-ai-<slug>-emergency-audit-api`、ワーカーは `/run/fire-ai-<slug>-emergency-audit-worker` を使い、それぞれ0700で作られる。片方の停止時に、もう片方の一時領域を削除しない構成である。ワーカーの事前確認に使うmanifestは `/etc/fire-ai/<slug>-emergency-audit-native.json` に配置する。API起動にOCR/モデルの事前確認を必須化していないため、読取装備の不調で通常の事務機能まで起動不能にしない。

配置順は、専用venv・migration・通常DBロールの権限、鍵、承認済みOCR/manifestを整え、生成した設定と両unitを管理者が設置し、systemd設定を再読込してからAPIとワーカーを起動する。ワーカーの生存表示と合成帳票の一巡処理を確認する。予定バックアップは、登録済みのワーカーunitを設置してから有効にする。`systemctl enable`/`start` 等の実サーバー操作は生成器には含まれない。

管理担当者による単発動作確認：

```bash
/opt/fire-ai/venv/bin/python scripts/run_emergency_audit_worker.py --once
```

常駐起動は承認したservice経由とする。ジョブはDBに保存され、短いtransactionで取得し、ネイティブ処理中はDBの書込ロックを保持しない。15秒ごとに短いtransactionで生存確認を更新する。取得権は処理期限+90秒で失効し、失効した古い処理は結果を公開できない。再起動後は失効ジョブを再取得でき、一つのジョブは最大3試行。権限失効、旧版化、原本不一致、取消は公開を止める。

停止時はserviceのプロセス群を終了させる。異常な電源断・管理者による強制終了後には、一時領域に孤立した作業フォルダがないか管理担当者が確認する。動作中のジョブの一時領域を一括削除しない。tmpfsでもswap/休止状態・core dump等の扱いは実機の情報管理基準に従う。

## 5. 利用者画面と大量取込

内部サーバーの `/ui/emergency-audit.html` を既存ブラウザーで開く。まず合成データで「取込→読取→原本と候補の確認→チェック→原システムで訂正→訂正版の追加→再チェック」を通す。

一つの原本は25MiB/50ページまで。描画は12Mピクセル、読取テキスト/語数にも上限がある。上限や読取不能を正常終了・全面確認済みへ置き換えない。日本語OCRがなければ `OCR_LANGUAGE_UNAVAILABLE`、手書きモデルがなければ `NOT_CONFIGURED` と表示する。手書き・取消線は確認候補であり、正しい訂正後の事実へ自動反映しない。

件数が多い場合は、利用者が選択したファイルごとに原本・処理履歴を分けて受け付け、DB上の待ち行列で処理する。900件/1000件を同時にメモリーへ読み込む運用はしない。現地受入では実際のページ数・画像サイズ・同時利用と保管量を使い、処理待ち、停止/再開、重複取込、容量不足を検証する。未検証の件数/速度を保証値として設定しない。

本部で承認した様式と項目位置がない帳票は、項目が未対応のまま残る。様式を推測して正常と判定しない。正式ルールの承認、例外、人による読み取り確認も含めて、提出前に確認できた範囲を表示する。

### 初回に設定担当者が行うこと

「帳票とルール」で根拠資料・空の帳票を登録し、様式の対応表を作る。原本のページと入力欄の位置、値の種類、適用期間を指定し、ルールの条件と根拠を保存する。通常の報告書作成者が毎回この設定を作る運用にはしない。正式資料や適用が不明な項目は候補のまま残す。

保存した設定を選び、閲覧権限のある過去の報告書で「選択した報告書で影響を確認」を実行する。別の承認担当者が日本語で表示された条件・例外・根拠を原資料と照合し、「確認した設定を承認」で承認する。登録者本人や同じ職員に紐付いた別アカウントでは承認できない。登録後の変更は新しい版を作り、利用停止しても過去の判定に使った設定は消さない。

### 通常の報告書確認

1. 「報告書の確認」で帳票の対応表とPDF/画像を選び、「取り込みを始める」。過去原本は同じ様式ごとにまとめて選べる。紙自体をデジタル化する装置や既存OAからの一括出力を追加する機能ではない。
2. 原本を開き、読み取った候補と照合した欄だけを確認する。読めない欄や印刷されない欄はその状態で残す。空欄だと確認できた場合は明示的に空欄として保存する。
3. ルールセット、確認モード、適用日を選び、「保存した内容でチェック」。指摘の根拠と、未検査の範囲を読む。ローカルモデルを使う場合も、画像・本文の出力は確認候補として扱う。
4. 指摘への判断と、分かる場合だけ理由を記録する。訂正が必要なら既存OAで直して再出力し、「新しい版として取り込む」で保存する。新版を読み直して再チェックし、残った指摘・新しい指摘・未検査を確認する。

### 訂正確認用PDFを保存する

確認結果の下にある「訂正確認用PDF」を使う。詳細閲覧3権限に加えて `emergency.report.export` が必要。既存役割にこの権限を自動付与しない。

出力は現在原本に対する最新検査1件で、種別と「この検査範囲のみ」を表示する。原本の表示内容へ番号枠を付け、日本語の指摘理由・根拠・担当者確認の一覧を添える。読取不能、未検査、未確定、位置未特定を残す。ルール検査、本文AI、画像AIを別々に行った過去結果を勝手に合成しない。

未保存の読み取り変更、過去版、旧検査、処理中の原本では保存できない。生成中に権限・職員・セッション・原本版・設定が変化した場合も結果を渡さない。画面の案内に従い再読込または再チェックする。出力できたことは正式な提出許可を意味しない。

保存名は `emergency-review.pdf`。原本のコピーを含むため、実帳票と同じ取扱いで内部の所定の保存先を使う。原本ファイルは変更せず、電子署名や可変注釈、リンク、添付ファイルを新PDFへ引き継がない。PDF閲覧ソフトで注釈表示を切っても番号・指摘が印刷されるよう、ページ内容へ描画する。

上限は原本50ページ・描画1ページ12Mピクセル・生成120秒・PDF32MiB・指摘一覧50ページ。上限超過時は省略版を成功として返さない。日本語の表示・印刷・枠位置は、正式帳票の実機検証でも照合する。

### 5指標と改善に使う記録

「作業記録」では比較区分を初回チェック前に登録する。導入前の比較群へAIを使った記録を後から移して、比較を良く見せることはできない。作業の開始/停止で実作業を記録し、画面外の訂正時間も必要に応じて追加する。実際のOAでの提出日時と、決めた期間の提出後追跡を記録する。

指定した別担当者は、各検査結果に対応する原本を開き、指摘のない欄も含めて独立に確認する。同じ誤りへの再チェックは同じ誤りへ明示的に紐付け、読取不能や未確認を正解扱いしない。時間・提出日時の入力を間違えた場合は履歴から訂正し、以前の記録を残す。

「測定記録を保存」で評価用JSONを取得し、「5つの評価指標を開く」から評価管理画面へ渡す。数値目標、比較条件、観察期間、正解確認を自動で承認しない。「訂正・誤警告の傾向」は選択中または現在一覧の範囲を明示して表示する。理由不明の事例から原因を捏造せず、確認できた傾向を次のルール変更案に使う。

## 6. バックアップと復旧

既存の本部別バックアップでは、APIだけでなく **監査ワーカーをwriter unitとして登録**する。該当本部の `FIRE_AI_BACKUP_WRITER_UNITS` に、実際の `fire-ai-<slug>-emergency-audit-worker.service` と他の書込service/timerを入れる。APIの主serviceは既存バックアップ処理が別途停止する。追加したワーカーを登録しなければ、DB dumpと原本保存先を一組として取得できたとは扱わない。

`--emergency-audit` で生成した `backup-<slug>.env` には監査ワーカーが最初から入る。ただし、既存の同期・取込等のwriter一覧は生成器から把握できない。**生成された初期一覧で既存一覧を置換せず、すべての稼働writerを合流させる。** 登録したunitが未設置ならバックアップは停止する。設置済みで停止中のワーカーはバックアップ後も停止のまま、開始前に稼働中だったワーカーだけを再開する。

バックアップ時の停止フラグは、停止操作の代わりにはならない。手動CLI・取込処理も停止し、保守ロックを確認する。予定バックアップは登録unitを停止し、終了後に以前稼働していたunitを再開する仕組みを使う。

復旧には次の組を対応させる。

1. 対象本部/対象release/migrationに対応するDB。
2. 同じ時点のstorage内の暗号化原本。
3. その暗号文に対応する監査用AES鍵（別経路で保管）。
4. バックアップ全体を暗号化している場合は、その復号鍵。

同UUIDの隔離した復元先でDBとstorageを復元し、対応する鍵を配置する。通常DBロールの権限を再適用し、原本ハッシュ、過去版、確認値、チェック履歴、未完ジョブの再開、取消済みジョブの非再開を確認してから再開する。AES鍵を通常バックアップへ同梱しない。キーの管理IDと復旧担当者は別の管理台帳で追えるようにする。

## 7. 更新と受入記録

利用者端末の追加インストールは不要。サーバーのrelease、migration、ネイティブ配布物、モデル、ルール/様式をそれぞれ版管理する。更新前に全writer停止と整合するバックアップを取り、テスト環境で影響検証し、承認後に本番へ適用する。ネイティブ本体・言語データを変えたらmanifestも承認し直してホストチェックを行う。戻す場合もDBの互換性、原本、鍵、設定の組を維持する。

本部別unitの更新では、APIだけでなく監査ワーカーの `WorkingDirectory`、`ExecStartPre`、`ExecStart`、venvも対象releaseへ揃える。同時に監査を外す場合は、取込とワーカーを停止・無効化し、監査フラグをfalseにしたうえで、停止を確認したunitをバックアップwriter一覧から外す。稼働可能なワーカーを先に一覧から外さない。保管済みデータの復旧用AES鍵は残す。

本番前には、専用権限・他本部拒否・担当/異動後の権限失効・外部通信/ログ・原本整合・復元・実機性能を実測する。AIを使う場合は、ローカルモデルサービス自体の外部通信とログ保存も確認する。loopbackへの接続だけでは、サービス全体の情報管理の実証にならない。

実帳票の独立した正解確認と提出後追跡を行い、訂正率、提出前検出率、誤警告、確認+訂正の総作業時間、未読/未検査と安全性を測定する。合成テストの成功を実帳票での改善実績に置き換えない。
