# 過去帳票によるモデル再学習：必須の実装・受入仕様

この文書は、救急報告書確認機能に追加する必須の残件を定める。現時点でトレーナーの実装、実帳票での学習、対象実機での実行、精度改善を証明するものではない。
過去帳票を用いた実際の勾配計算・重み更新・保存・再読込・独立評価を完成条件に含める。訂正傾向の集計、置換辞書、RAG、prompt変更だけで再学習完了に置き換えない。

2026-11-22のクラウド続行で、[独立正解・family・固定dataset登録API](TRAINING_REGISTRY.md)を追加。
これは§3–4の先行実装で、トレーナー、実帳票での重み更新、実機評価の完成ではない。
APIは `model_training_performed:false` と `training_ready:false` を保持する。

## 1. 現在地

| 項目 | 現在の実装 | 必須の追加・確認 |
| --- | --- | --- |
| 訂正・誤警告の傾向 | `emergency_audit_learning.py` の読み取り専用集計。`model_training_performed:false` | 学習用データへの独立した審査・版管理 |
| 正誤の独立確認 | 作成者と異なる職員による正誤・誤りID・読取状態・全体確認 | 正しい転記、訂正対象範囲、訂正先とその根拠の暗号化記録 |
| 原本・履歴 | 専用保管、原本版、不変の検査履歴 | 改訂・再取込・再スキャンを束ねるfamilyと固定dataset registry |
| ローカルAI | 設定されたモデルへの推論と、未確認候補の形式・引用検証 | 実トレーナー、学習job、重み・checkpoint・基盤モデルのregistry |
| モデル配備 | 設定されたモデル名を使用 | 固定artifactによるadapter/モデル配備、独立評価、昇格、rollback |
| 5指標 | 測定記録・独立確認・不変評価の仕組み | 正式帳票・対象実機・実運用での測定と目標判定 |

汎用の `learning_engine.py` は `literal-correction-v1` の置換処理であり、この実学習経路には数えない。

## 2. 実帳票・実機の基準確認を先に行う

正式な入力要領、適用期間、実様式と原本を確認し、現行処理の読取誤り・見逃し・誤警告・未検査を独立評価する。
対象実機のOSと実行環境、GPU認識・利用可能メモリ、RAM、空き容量、OCR、既存モデルの形式・ハッシュ・利用条件を確認する。ホストのGPU情報だけで別実行環境の利用可否を確定しない。
現行native readerはLinux専用で、既存host checkはGPUと実モデルを未検証とする。AI接続はloopback固定であり、別環境との接続やWindows対応を確認済みと扱わない。
この基準結果を受けて、最初に学習するタスクとモデルを選ぶ。本文の記載確認と画像・手書き読取は別タスクとし、一方の改善を他方へ広げて主張しない。
LoRA等の追加パラメータ学習は候補方式とする。具体的なモデル、ライブラリ版、量子化、入力長、batch、必要容量・処理時間は未確定で、実測して固定する。

## 3. 独立した教師データ

- 原本版・SHA・様式版・根拠資料版・適用時点に結び付く、暗号化された正解記録を追加する。
- 原本に実際に書かれた文字の転記と、内容として妥当な訂正先を別項目にする。誤記を転記段階で消さない。
- 項目ID、ページ、文字範囲または矩形、誤りの種類、許容される訂正、根拠、独立確認者と確認版を保持する。
- 判読不能、取消線、複数の解釈、誤った手書き、訂正後にも残る誤りを保持する。「訂正済み」「最終版」「警告へ同意」だけで正解にしない。
- 未確定項目を、確定した教師ラベルや「問題なし」の負例にしない。指摘なしの教師例には、その対象範囲全体の独立確認を要する。
- 学習入力は判断時点の原本・読取結果に固定する。訂正後の値、正解ラベル、後から分かった情報を入力へ混ぜない。
- 訂正前原本が存在しない場合、元の誤りを推測で復元しない。利用できる学習対象と不足を記録する。
- 原本の記載、当時の規則への適合、現在の規則による確認を区別する。旧規則に適合した記載を無条件に誤りへ変換しない。

モデルが出した候補のID・文章を正解の単位にせず、モデルに依存しない誤りIDと位置を使う。見逃しも原本全体の独立確認から登録する。

## 4. family分割と不変の基準

同一事案・報告書の原本、訂正版、複製、再取込、再スキャン、切出し、加工・拡張例は同じfamilyへ所属させる。ファイル名や行番号だけで分割しない。
family確定後にTrain・Validation・Holdoutへ分割し、原本・正解・前処理版を含むmanifestを固定する。同じfamilyを区分間に跨がせない。
対応不明や重複疑いは隔離し、理由と件数を保持する。後から追加した派生物にも既存familyの区分を継承させる。
Trainだけで重みを更新し、Validationで設定・停止時点・閾値を選ぶ。最終Holdoutの原本・正解は学習workerへ渡さない。
Holdoutの結果を調整に使った場合は、その履歴を残し、以後「未見の最終評価」として再利用しない。正解訂正は新dataset版とし、旧版を書き換えない。

比較する基準モデルも不変artifactとして固定し、Candidateと独立して再ロードする。学習処理で同じモデルオブジェクトを変更し、基準側まで変わることを防ぐ。
モデル比較のbaselineと、既存の運用区分 `baseline`（支援なし）は別である。現行の支援なし区分にはAI検査を実行できない。
過去帳票の再実行は固定技術benchmarkとして記録する。現在生成した警告を過去の提出前警告として扱わず、過去の作業時間・訂正前の状態を補完しない。

## 5. 実学習と再現可能な証拠

専用training jobとworkerを追加し、通常の読取・CRUDを継続できる構成にする。学習は必須工程だが、帳票の登録・訂正だけで本番モデルを自動更新しない。
各jobは本部、依頼者、対象権限、dataset、基盤モデル、tokenizer、prompt、様式・ルール・前処理、コード・依存資材、学習設定の版とdigestを固定する。
推論jobと検査履歴にも使用artifactと推論設定を固定し、「最新」という可変名だけで結果を識別しない。

学習完了の証拠は次をすべて要する。

1. 対象データとTrain分割の一致、学習可能パラメータ、実行したoptimizer step数。
2. 有限のloss・gradientと、実際に変更された学習tensorの記録。ログ文言やファイル作成だけでは不足。
3. 保存した重み・設定・基盤モデルのdigestと、変更していない基準モデルの確認。
4. 新規プロセスでの再ロードと推論。学習した重みが実際の候補生成に使われること。
5. 固定Validation・Holdoutとの比較結果、失敗・未検査・対象外・欠測の件数。

再開時はcheckpoint、dataset、設定、stepの対応を確認し、異なるjobの状態を混ぜない。OOM、容量不足、権限失効、lease喪失、途中終了を完成扱いにしない。
配備形式へ変換する場合は、変換後の実artifactでも同じ固定評価を行う。adapterと基盤モデル、推論runtimeの互換性を実機で確認する。

## 6. private保管とoffline実行

- 原本、教師データ、token・画像cache、adapter、結合モデル、checkpoint、詳細評価を本部専用の保護対象とする。外部サービス、公開repository、汎用文書・学習資料へ送らない。
- 読取済み原本の暗号化だけで完了にせず、学習の一時領域・ログ・異常終了後の残存・バックアップも検証する。秘密値や本文を通常ログ・例外・実験追跡へ出さない。
- 既存vaultの32MiB上限を踏まえ、モデル用の認証付き分割保管とmanifestを設計する。本部・artifact・分割順・長さ・欠落を検証し、鍵は保管物と分離する。
- 承認したローカル資材のみを読み、不足時は停止する。実行中のモデル取得、外部telemetry、upload、任意の外部コード実行を許可しない。
- offline設定に加えて実行環境で外部通信を制限し、通常・失敗・再開時を実測する。loopback接続だけを情報保護の証明にしない。
- 正解撤回・削除時は、派生dataset・adapter・checkpoint・配備モデルまで系譜を追跡し、保管期限、停止、再学習、復元の扱いを定める。

## 7. 評価・承認・rollback

Candidateは固定基準モデルと同じ原本・正解・入力範囲で比較する。読取不能・未検査・候補なしを「正しい」に変換せず、誤警告削減と見逃しを同時に評価する。
学習済みでも改善しなければCandidateのまま保持する。独立した確認者がHoldout結果、対象範囲、原本の根拠、実機の保護・復旧を確認して昇格する。
昇格は固定artifactへの参照を明示的に切り替え、既存基準モデルと履歴を保持する。処理中の旧結果を新版の結果にしない。劣化・不適合時のrollbackを実操作で検証する。

[5指標の測定仕様](ACCEPTANCE_MEASUREMENT.md)に従い、提出後訂正率、提出前発見率、誤警告、合計作業時間、読取・未検査と保護を確認する。
固定帳票benchmarkから実際の提出前成功や訂正削減を作らない。実運用の提出・警告時刻、全作業区間、追跡、独立正解を記録し、学習・正解作成の負担も別掲する。
数値目標、最低標本数、比較条件、許容劣化、追跡期間は未確定である。実測と評価計画を基に最終Holdout判定前に固定し、未設定・不足・未確定のまま合格にしない。
実学習の成功、技術benchmarkの改善、5指標の達成、本番受入は別の状態として記録する。

## 8. 実装・受入の確認順

1. 正式帳票・実機・現行処理の基準結果を記録し、最初の学習タスクと資材を決める。
2. 独立正解・family・固定分割・基準artifactを整備し、改訂・再スキャンの分割漏えいを拒否する。
3. 合成の小規模モデルでも実際の重み更新・保存・再ロードを試験し、実装を検証する。
4. 対象環境で過去の実帳票を用いて学習し、固定評価と配備形式の比較を実施する。
5. 容量不足、停止・再開、権限失効、改訂、誤ったcheckpoint、通信・一時領域・復元を検証する。
6. 独立承認後の運用で5指標を測定し、未達・不明を残して受入判断する。合成試験だけでこの必須工程を完了にしない。
