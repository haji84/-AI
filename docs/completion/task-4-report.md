## Exactness, locks and compatibility

Supported individual money magnitude is at most `9999999999999999.99` with at most two fractional places and the approved year's stricter configured precision. Nonfinite values, overflow, extra decimals and monetary float inputs through new financial schemas reject; no implicit input rounding. The largest amount survives multiple one-cent transfers, commitments, repeated payments and CSV/XLSX export/reimport.

PostgreSQL remains native NUMERIC(18,2), including the common contract column; historical migrations were not rewritten. SQLite new exact columns store canonical decimal text. SQLite amount format/sign constraints inspect characters/positions rather than numeric ordering of TEXT. Accounting sums/comparisons run over loaded Python Decimal values, not SQL SUM or monetary TEXT ordering/casting. Signed amendments and journal compensation remain valid. Direct ORM binding rejects unsupported scale/nonfinite/overflow before database conversion. PostgreSQL native finite/sign constraints additionally reject invalid stored authority.

Existing SQLite NUMERIC-affinity contract tables do not become TEXT merely from the new mapping. Both legacy and financial writes refresh the persisted value before commit and reject detected loss of the exact submitted amount. Tests reproduce max-magnitude legacy-affinity loss and require422/rollback; compatible smaller existing writes retain their values. Prior rounded/binary numeric values cannot recover lost original digits. Historical source values must be reconciled against retained originals and Human judgment; the adapter does not claim reconstruction of lost precision. Legacy JSON float payloads at magnitude1e12 or above reject before Decimal parsing and require an exact string or integer. Ordinary legacy float/int compatibility remains; exact original money should be submitted as Decimal strings. The old float response is compatibility output, not financial authority.

Transaction ordering locks sorted accounts, then a fresh sorted common contract/vendor/Document set and relevant proposals/events. Standalone proposal/reversal originals, distinct amendment/event/candidate originals, and import originals/row evidence are included; locks remain until commit. Locked reads force-refresh loaded ORM evidence. Reversal render authorization follows the target common contract and raw restricted snapshots do not enter returned manifests. Review snapshots compare account/policy/contract/vendor/source hash versions again before posting. The actual PostgreSQL test executes migration048, proves native precision/serialization, races payments with separate sessions, rejects replay, attempts concurrent common contract/vendor/Document writes while locks are held, and exercises append-only guards. PostgreSQL/Chromium verification is required in actual CI; local skip does not prove these checks.
