# パスワード有効期限と本人更新

正式仕様v2.0 §6に従い、既存Employee/User/session/RBAC/password historyを使う。端末への追加インストールは不要。本部ごとのDBと実行環境の設定で管理し、別本部へ設定・アカウントを共有しない。

## 管理者

`FIRE_AI_PASSWORD_MAX_AGE_DAYS`はHumanが選ぶ本部方針。有効範囲は1〜3650日。未設定なら自動の一律期限を付けず、アカウント管理画面から明示日時を設定できる。90日等をAIが勝手に決めない。生成される本部envには設定方法をコメントで示す。初期管理者作成とアプリ実行に同じ本部方針を使う場合、owner用envとruntime用envの両方へ同じ値を設定し、本部アプリだけを再起動する。方針変更だけで既存パスワードの期限を書き換えない。

アカウント管理の有効期限フォームで対象者・操作・理由を確認する。

- 本部方針の適用: 最終パスワード変更日＋設定日数を期限にする。適用操作の現在時刻から延長しない。
- 日時指定: 端末の時刻帯で選び、APIへ時刻帯を含むISO8601として送る。過去日時を指定すると次の本人確認で更新必須となる。
- 解除: Humanの理由付き操作で現期限を解除する。次のパスワード更新ではその時点の本部方針を再適用する。

いずれもexpected_versionによる競合検出、account.manage、有効な職員状態、ロック後の権限/期限再確認、監査を必要とし、対象者の全セッションを失効する。期限設定はパスワードを変更せず、hash/履歴は返さない。最後の管理者のRole保護を維持し、管理者自身も本人更新で回復できる。パスワードを忘れた職員は、権限を持つHuman管理者が従来のreset手順で再設定する。

## 利用者

期限切れのパスワードで本人確認はできるが、業務データの閲覧・更新、権限一覧、管理操作、学習操作は利用できない。既存のログイン状態でも期限到来後は拒否する。業務ブラウザは固定の`/ui/password.html`へ移動する。

1. ログインIDと現在のパスワードで本人確認する。
2. 現在のパスワード、新しいパスワード、確認用の新しいパスワードを入力する。
3. 更新後、すべてのログイン状態が失効する。新しいパスワードで再ログインする。
4. 「業務画面へ」から戻る。

新パスワードは12〜128文字。現在と直近5世代を再利用できない。画面は送信後にパスワード入力を消去する。無効化・退職・利用不可の職員やアカウントは、期限切れ本人更新を使って再有効化できない。本人更新は正式業務データや権限を変更しない。

## APIと移行

`/auth/login`と`/auth/me`は本人のpassword_change_requiredと期限を返す。期限切れ業務APIは403、detail.code=password_expired、固定の更新URL、X-FireAI-Password-Renewal=requiredを返す。更新用本人確認を許すのは`/auth/me`、`/auth/logout`、現在secretの検証付き`/administration/password`だけ。通常のcurrent_userと既存require_permissionを弱めず、別の本人確認dependencyでこの3操作を限定する。

Migration045（公開前にmainとの番号照合が必要）はapp_usersへpassword_changed_at/password_expires_atを追加する。現hashに一致するpassword historyの最終日時を使い、履歴がなければcreated_atを使う。既存hash・既存アカウント状態・原本を変えず、既存expiryは未設定で開始する。既存職員へ期限を付ける場合はHumanが対象を確認して本部方針を適用する。新規bootstrap/create/change/resetは、その時点の本部方針で日付を設定し、監査は日付・設定日数・失効事実だけを保持する。

通常の本部更新手順でbackup、停止、owner接続migration、生成grants再適用、共通codeの本部release切替、起動、本人更新/業務権限の確認を行う。別本部のDB・原本・backupへアクセスしない。migration番号以前のcodeへ単純に戻して期限を無視する運用はしない。旧releaseへの復帰はpaired backupと承認済み復元手順で行う。

## 検証・制約

Synthetic HTTPで期限到来、ログイン制限、全セッション失効、本人更新、再利用拒否、Human設定/解除/方針適用、CAS、無効職員、ロック後の期限再確認を検証する。同じHTTPテストと既存データ移行を実PostgreSQL CIで行い、Chromiumは期限切れログイン→固定ページ→更新→再ログイン→業務利用を確認する。実端末/本部の採用日数・実運用受入をAIが代行しない。
